### Added

- Secure channel, handshake (`Protocol.Transport.Secure`, not yet used by the tiers): `SecureHandshake` runs the three fixed-size messages of `doc/dev/secure-channel.md` on a stream, as the client or the server. Both signatures (ECDSA P-256, IEEE P1363) cover the hashes of both TLS certificates of the session, both nonces, both ephemeral keys and both key ids, under labels naming the version, the link and the role. Every point received is checked on the curve by the channel itself (`P256`), and every signature value in range, before any import. A pinned key that is the key of the TLS certificate of the peer is refused, and the last step checks that the key of the peer is still pinned now. `KeySchedule` derives one key and one IV per direction with HKDF-SHA256, every intermediate secret erased. A failure throws a `SecureChannelException` with its reason from a closed list (`SecureChannelFailure`), and nothing is sent to the peer.
- Secure channel, keys: `SigningPublicKey` reads a public key in one normalized form (named curve P-256, uncompressed point) and names it by the SHA-256 of that form (its key id). `SigningKeys` loads the signing key of a tier (encrypted PKCS#8 PEM) and the file of the public keys of its peer, refuses to start (fail closed) on a wrong password, a password equal to the one of the PFX, 0 or more than 4 keys, a duplicate, its own key or a signing key equal to its TLS key, and takes the files again before each new connection and every minute, by time and SHA-256 of their content; a removed key raises `PeerKeysRemoved`, each listener told on its own (a failing one logged, event id 9063); files that stay refused are logged again every 5 minutes, with the time since the keys in use were taken; the file of the peer is read as UTF-8 (a byte order mark accepted, UTF-16 refused); an unknown key id is carried by the `SecureChannelException`, for the logs. The "Handshake" settings (`SigningKeyPath`, `SigningKeyPassword`, `PeerPublicKeysPath`) and their validator. Event ids 9057-9060 and 9063.
- Certificate authority tool: `signing-key --role <back|veryback> --out <folder>` creates the signing key of a tier, encrypted with `BOARDGAMESPLATFORM_SIGNING_KEY_PASSWORD`, and the line of its public key for the peer.
- Tests: the primitives, the key schedule, both labels and the composition of the transcript against vectors computed by the Python package `cryptography` and an HKDF written from RFC 5869 (`generate_vectors.py`, never the code under test), RFC 5869 case A.1; the handshake over loopback sockets: agreement, a key not pinned on each side, other certificates on each side, a signing key that is the TLS key, a key removed during the handshake, no certificate, changed first, second and third messages, an ephemeral key replaced in the middle, the signature of the server sent back, random and mutated messages with fixed seeds, a replayed handshake, both signatures checked over a transcript composed field by field; the load and the reload of the key files.
